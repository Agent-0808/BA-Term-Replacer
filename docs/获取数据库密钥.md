## 二、为什么只能动态取，不能静态提取

游戏把密钥拆成 3 段 `byte[]`（10 + 10 + 12 = 32 字节）存在 `KeyData` 类里，运行时拼接后再转成 64 字符 hex，通过 SQLCipher 的 PRAGMA 注入：

```
1. PRAGMA cipher_license = '<License>'   → ExecuteNonQuery
2. KeyData 三段拼接 → byte[32] → hex
   PRAGMA key = "x'<hex>'"               → ExecuteNonQuery
```

- 6/8/11 三个版本的密钥分段（10/10/12）以及整段 32 字节，在 `GameAssembly.dll` 里搜索**全部 0 命中**——字节是代码逐字节写出来的，DLL 中不存在明文。
- 因此没有"静态扫一下文件"的取巧办法，只能在密钥被拼出来的那一刻从寄存器里拿。好在拦截点跨版本极其稳定，三版都是一条固定特征码。

***

## 三、拦截点原理（为什么这条特征码可靠）

IL2CPP 是 AOT 编译，同一份源码 + 同一套工具链产出的机器码指令序列一致，只有 rip 相对地址和 rel32 调用位移不同。密钥构造段固定是这个形状：

```asm
48 8B 0D xx xx xx xx     mov rcx, cs:KeyData类指针
83 B9 E0 00 00 00 00     cmp dword ptr [rcx+0E0h], 0    ← 类初始化检查
75 xx                    jnz short
E8 xx xx xx xx           call il2cpp_runtime_class_init
48 8B 0D xx xx xx xx     mov rcx, cs:KeyData类指针
48 8B 81 B8 00 00 00     mov rax, [rcx+0B8h]            ← static_fields
48 8B 48 18              mov rcx, [rax+18h]             ← KeyData 对象
48 85 C9                 test rcx, rcx
0F 84 xx xx xx xx        jz
31 D2                    xor edx, edx                   ← 特征码起点
E8 xx xx xx xx           call 拼接函数（3 次 BlockCopy 10/10/12）
48 89 C2                 mov rdx, rax                   ← RAX = byte[32] 原始密钥
E8 xx xx xx xx           call byte[] → hex
48 89 C3                 mov rbx, rax                   ← 这里读 RAX 即 64 字符 hex
48 8B 05 xx xx xx xx     mov rax, cs:KeyData类指针
48 8B 80 B8 00 00 00     mov rax, [rax+0B8h]
48 8B 50 20              mov rdx, [rax+20h]             ← License 串，给特征码收尾
```

特征码就是把中间"`xor edx,edx` → 两次 call → `mov rbx,rax`"这段指令原样抄下来、把地址和位移换成 `??`，再带上一小段 `KeyData → static_fields → License` 作为防误伤。**不要用旧版本记录的绝对 RVA 去推算**，每版直接用特征码搜。

## 四、前置条件（踩坑记录）

1. **必须以管理员运行**：Steam 以管理员启动时游戏进程是 High 完整性级别，普通权限的 pwsh / CE 拿到的是 `OpenProcess(PROCESS_VM_READ) → err=5`、模块枚举 0 个。表现就是"进程在跑但看不到 `GameAssembly.dll`"、"CE 说没有可读内存"。游戏本身不是 PPL 保护进程，提权到同一级别即可。
2. **加速器也得开**：不开时游戏卡在网络/版本检查，走不到预加载开库，断点永远不会命中——这是"断点下好了但游戏不停"的最常见原因。
3. **必须冻结进程再 attach**：`ExcelDB.db` 在启动预加载阶段就被打开，手动 attach 基本来不及。先冻结、再从容操作、最后放行。

## 五、操作步骤

两种模式二选一，前置条件相同（见第四节）。模式 A 少两步操作，模式 B 每一步都可见、方便排查。

### 模式 A：半自动（推荐）

**A1. 启动 watcher（管理员 pwsh）**

```powershell
pwsh -File scripts/suspend_until_gameassembly.ps1 -AutoContinue
```

**A2. 从 Steam 启动游戏**

等 watcher 打印 `GameAssembly.dll 基址 = 0x...` 和"已挂起"。

**A3. CE 连接进程并执行 Lua（管理员）**

启动 Cheat Engine → Open Process → `BlueArchive.exe`（脚本也会尝试自己连，但 CE 通常会弹进程列表让人选）。

然后 `Table → Show Cheat Table Lua Script` → 载入 [find_db_key.lua](../scripts/find_db_key.lua) → Execute。脚本沿用已 attach 的进程，按当前基址重扫特征码并在命中点 `+0xF` 下硬件断点，然后写标记通知 watcher。

**A4. 等结果**

之后不需要任何操作。watcher 检测到标记自动放行，命中后由它在终端打印：

```
KEY = 05f5...
校验通过：密钥可打开 work\db\ExcelDB.db（469 张表）。
```

### 模式 B：手动

**B1. 启动 watcher（管理员 pwsh）**

```powershell
pwsh -File scripts/suspend_until_gameassembly.ps1
```

**B2. 从 Steam 启动游戏**

等 watcher 打印基址和"已挂起"。

**B3. CE 打开进程**

管理员启动 Cheat Engine → Open Process → `BlueArchive.exe`。

**B4. 扫描特征码**

- Scan Type `Array of Byte`，勾 `Hex`，Value 填第一节的特征码
- Memory Scan Options **只勾 `Executable`**（代码段是 `PAGE_EXECUTE_READ`，勾 `Writable` 会把它排除）
- Start / Stop 填绝对地址（`基址` 与 `基址+EF53000`），或者两个都留空扫全空间

预期 `Found: 1`，结果一栏显示 `GameAssembly.dll+1BFC38F`。

**B5. 下硬件断点**

在 CE 的 Lua 窗口载入 [find_db_key.lua](../scripts/find_db_key.lua) 执行。这一步与 A3 相同，会再扫一次特征码并下断点（重复扫描无副作用），只是 watcher 不在等标记。

**B6. 放行取密钥**

回 watcher 窗口按回车。命中后 CE 的 Lua 窗口打印 `KEY = ...`，游戏被 CE 暂停属正常现象。

> 两种模式共用 `%LOCALAPPDATA%\batr\` 下的 `.key_hook_ready`（断点就绪）和 `db_key.txt`（密钥）做握手，watcher 启动时会清掉上一次的残留文件。

### 校验（可选）

```powershell
uv run python -c "from batr.db import connect, list_tables; c = connect(r'D:\SteamLibrary\steamapps\common\BlueArchive\BlueArchive_Data\StreamingAssets\PUB\Resource\Preload\TableBundles\ExcelDB.db', '<密钥>'); print(len(list_tables(c)))"
```

打印 `469` 即成功（表数量随版本会变，能正常打开、不抛 `DatabaseError` 就算对）。

## 六、故障对照表

| 现象                                                 | 原因                                                     | 处理                                  |
| :------------------------------------------------- | :----------------------------------------------------- | :---------------------------------- |
| 脚本一直停在"等待 `GameAssembly.dll` 加载"，或 CE 扫描报无可读内存     | 工具权限低于游戏进程（Medium vs High）                             | 用管理员身份重开 pwsh / CE                  |
| CE 扫描 `Found: 0`                                   | 只勾了 `Writable`，代码段不可写                                  | 勾 `Executable`                      |
| `Scan error: controller: No readable memory found` | `Writable` 与 `Executable` 同时勾，CE 要求"既可写又可执行"           | 只勾 `Executable`                     |
| `Unhandled exception: Invalid stop address`        | Start/Stop 里写了 `GameAssembly.dll+EF53000` 这类符号表达式，解析失败 | 填绝对地址，或两个都清空                        |
| 断点下好但游戏一直不停                                        | 没开加速器，卡在网络检查，走不到开库；或流程走完太慢，开库已过                        | 开加速器重来，全程别超过一两分钟                    |
| `KEY =` 为空                                         | 断点位置读错寄存器                                              | 断点改到 `hit+0x12`，改读 `RBX+0x14`       |
| 断点命中但密钥打不开库                                        | 抓到的不是 key（比如误停在 license 相关路径），或库里换了机制                  | 先用第二节的特征码再核一次命中唯一性；仍失败就走运行时字符串法（见下） |
| `-AutoContinue` 一直不放行，最后超时放行                        | CE 里没执行 Lua、执行报错，或 `openProcess` 没打开 `BlueArchive.exe` | 看 CE 的 Lua 窗口输出；确认 `%LOCALAPPDATA%\batr\.key_hook_ready` 是否生成 |

**兜底方案**：若某版特征码失效（机制被改），CE 扫 UTF-16 文本 `PRAGMA key` → 对字符串地址右键 `Find out what accesses this address` → 跑一次开库，访问它的指令就是拼接点，此时寄存器里就是 hex 密钥，不依赖任何静态特征。

## 八、自动化现状

- **已实现（半自动）**：`scripts/suspend_until_gameassembly.ps1 -AutoContinue` + `scripts/find_db_key.lua`。两个脚本通过 `%LOCALAPPDATA%\batr\` 下的标记文件握手，放行、取密钥、校验全自动，只剩"开 CE、选一次进程、点一次 Execute"需要人手。
- **未实现（全自动）**：Python 版 `batr key`，自研调试器（`DebugActiveProcess` + 硬件断点 + 读 `CONTEXT`），可彻底摆脱 CE；动手前需要先验证游戏是否检测 `PEB.BeingDebugged`（CE 用的是 VT 调试器，验证不了这一点）。
